# Taste
- Communicates in Chinese and expects replies (and code comments / user-facing copy) in Chinese. Confidence: 0.9
- Gives terse, high-level requests — often bundling several features or bug reports (as a numbered list) into one short message — and expects the agent to autonomously explore, plan, and implement/diagnose end-to-end (including version bump, CHANGELOG/README updates, and build verification) rather than being walked through step by step. Confidence: 0.65
- When presented with design-choice questions, accepts the agent's recommended option wholesale instead of deliberating each choice individually. Confidence: 0.55
- Pushes back on over-engineered fixes: when a bug has a simple expected behavior (e.g. "delete the course, then the page closes"), wants the direct, minimal fix rather than a broad multi-file redesign, and will call out that the solution is "过于复杂". Confidence: 0.65
- But when the real cause is a wrong data model (e.g. period number derived from row order), chooses the principled structural fix — decouple the domain value from its position, delete the now-meaningless mapping table — over the quick patch to the hardcoded table, even when the agent flags it as the much larger change. Confidence: 0.5
- Holds a high bar for UI/UX fidelity: expects named UI patterns to match their real definition (a "floating" nav bar must genuinely float above content, and the agent should first find out what the proper pattern is — "你要先搞清楚什么叫真正的悬浮式导航栏"), treats poor legibility/contrast as a defect to fix (e.g. flagging the timetable's left time gutter as "太看不清"), wants editing flows to be 人性化 (user-friendly), and treats visually jarring styling (e.g. dark containers clashing with the theme, on the settings page or elsewhere) as a bug to fix, not a nit. Confidence: 0.65
- Describes bugs by concrete user-visible steps and symptoms (what they did, what happened) and expects the agent to reproduce/trace that exact path and pinpoint the root cause, not just apply a plausible patch. Confidence: 0.55
- Expects "提交" to cover the full publish flow — commit *and* push to the remote (e.g. `git push origin master`) — and will point out when work is only committed locally ("那你要给他上传啊"). Confidence: 0.7
- Treats a version bump (`versionCode`/`versionName`) and matching CHANGELOG entry as part of finishing a change set, not a deferred release step — will challenge the agent for skipping it ("怎么不改版本号？") or outright order it ("改版本号") rather than accepting a "didn't proactively release" default. Confidence: 0.7
- Expects the agent to commit its finished work as part of the task flow without waiting to be asked; if changes are left uncommitted it will prompt "写完后提交啊！". Confidence: 0.6
- When a bug survives an attempted fix ("好像还是有点问题" / "规则还是有问题"), expects the agent to stop tuning the same heuristic and instead get to the real cause — dig deeper, research how comparable open-source projects solve it ("看一下人家是怎么写的") or the formal definition of the pattern, and if the logic itself is wrong, rewrite or remove it outright ("重新写") rather than layering on more special-case patches. Confidence: 0.65
- Will also directly order a whole screen rewritten ("这个页面你重写算了") when its editing flow is fundamentally inadequate, rather than asking for incremental patches to it. Confidence: 0.5
- Wants stored records to hold their own concrete values rather than being recomputed from shared settings: once imported/created, a course's clock times and other specifics should be pinned so later edits to the global timetable (or importing a different school) never retroactively shift existing entries. Confidence: 0.5
- Prefers authoritative input (e.g. a school-specific import script's own timetable) to be applied automatically instead of gated behind a user opt-in checkbox, as long as the effect is stated plainly on screen rather than applied silently. Confidence: 0.5
- Connects Android test devices via wireless (Wi-Fi) adb debugging, supplying the IP:port and pairing code for `adb pair`/`adb connect` (`10.x.x.x：port code`), rather than relying on USB debugging. Confidence: 0.5
- Communicates UI requirements by pasting a screenshot of another app as the reference, and explicitly asks for that interaction to be reimplemented "用我们自己的设计实现方式" — i.e. copy the behavior/UX model, but translate it into the project's own design system (its own color tokens, typography, line weights, component language) instead of cloning the reference's styling. Confidence: 0.7
- Stays on the stated problem and waves off tangential findings the agent raised itself ("那个不用管"), redirecting the discussion back to the specific subject at hand. Confidence: 0.45
- Expects the agent to actually finish work it previously reported as not done: when a task ends by listing deferred/"未做" items as known limitations, the user follows up with "把没做的做一下" rather than accepting them as caveats — so self-flagged unfinished work is treated as debt to pay down, not an acceptable stopping point. Confidence: 0.6
- Wants redundant notifications suppressed: when an external source pushes notifications duplicating what the app already does itself (e.g. 雨课堂's own "上课提醒" vs the timetable's pre-class reminder), the app should not re-push them to the user ("如果它发送的是上课提醒通知，我们就不向用户推送了"). Confidence: 0.5
- Requires new features to be independently controllable: explicitly asks that added capabilities (e.g. background fetch, notifications) each come with their own dedicated settings page and on/off switches ("注意，这些功能要有独立的设置页面和开关"). Confidence: 0.6
- Values end-user customizability: asks features to expose user-adjustable options (e.g. widget content, style, and kind) through the app's own settings UI instead of fixed defaults, and wants the feature set broadened (more content, styles, and kinds) rather than a single hardcoded variant. Confidence: 0.5
- Treats separately-reported problems as independent issues and expects each diagnosed on its own rather than assumed to share a single root cause or bundled into one fix ("问题是单独的"). Confidence: 0.45
- Gates the stable release on their own real-device acceptance, and is explicitly fine with a pre-release/RC version in the meantime ("要确认没有问题了，或者你变成那种 RC 版本") — i.e. compile-passing + logic tests alone don't justify calling a release final, so shipping an RC when on-device verification is still pending is the desired behavior; will order it directly when committing ("提交一下吧，但是先搞个 RC"). Confidence: 0.65
- Wants release *metadata* to reflect that a build is unverified, not just the version string: an RC should also be published on GitHub as a pre-release/"beta" rather than a normal latest release (and expects the agent to infer this convention from a terse hint like "你懂吧？"). Confidence: 0.6
